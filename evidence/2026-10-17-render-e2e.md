# End-to-end run on Render: 2026-10-17

The first full run of both demo scenes on the **deployed** app (`https://nonna-mode.onrender.com`, deploy `513c1294`), with **real** PayPal sandbox approval, real OpenAI (`gpt-6-luna`), real Resend email, and the Trigger.dev recovery scan running every minute. Rosa was played in a normal browser (PayPal login as the sandbox buyer); Luca and Giulia in headless Chromium at 360 px. Provider IDs are shortened to their last five characters.

## Webhook evidence, per event

Sources: the Render log lines `[paypal-webhook] {…"verified":…}` and `[paypal-webhook] recorded {…"duplicate":…}` (07:55–08:40 UTC), plus the `webhook_event` rows. The route records an event only after `verify-webhook-signature` returns `SUCCESS` (unverified → 400, nothing stored). `paypal_event_id` is the primary key, inserted with `ON CONFLICT DO NOTHING`. **Linked to payment** means `webhook_event.payment_id` was set by matching the event's resource ID to the payment's stored PayPal order, authorization or capture ID; `custom_id` isn't used.

**Deduplication was not exercised in this run:** PayPal delivered each event exactly once, so no duplicate was received or ignored. Duplicate and concurrent-duplicate delivery are covered by the automated tests (required test 3, `test/webhooks.test.ts`, Neon test branch), not by this live run.

## Bug found and fixed during the run

- Sign-in links on Render redirected to `http://localhost:10000` (the proxy's internal address). Fixed in PR #8: redirects use `APP_BASE_URL`; the cookie's `Secure` flag follows the public scheme. A regression test fails on the old code.

## Polish found during the run (fixed with this evidence)

- The payer screens said "Luca or Giulia will check it" / "Now Luca needs to check it" for a payment **to** Luca. They now name only contacts who can actually approve.
- The contact header "Review request" truncated at 360 px; now "Review".
